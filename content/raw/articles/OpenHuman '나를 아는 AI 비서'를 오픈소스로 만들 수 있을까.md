AI 에이전트 도구가 쏟아지는 요즘, 대부분의 AI 비서에는 한 가지 근본적인 문제가 있다. 사용자를 모른다는 것이다. 매번 새 대화를 시작할 때마다 "저는 이런 업무를 하고요, 이 도구를 쓰고요"라고 맥락을 처음부터 설명해야 한다. OpenHuman은 이 문제를 정면으로 겨냥한 오픈소스 프로젝트다. 연결된 계정에서 데이터를 자동 수집하고, 로컬 머신에 메모리 트리(Memory Tree)를 구축해서, "몇 주가 아니라 몇 분 만에" 사용자를 파악하겠다는 것이 핵심 주장이다. 아직 얼리 베타(Early Beta) 단계이지만, "에이전트가 똑똑해지려면 먼저 기억해야 한다"는 설계 철학 자체는 짚어볼 가치가 있다. <박재홍의 실리콘밸리>

## 핵심요약

- OpenHuman은 로컬 메모리 트리와 118개 이상의 서드파티 연동을 결합한 오픈소스 AI 에이전트 비서로, 설치 후 계정 연결만으로 사용자의 전체 디지털 맥락을 파악하겠다는 목표를 갖고 있다.
- 20분 간격 자동 동기화(auto-fetch)로 Gmail, Notion, GitHub, Slack 등에서 데이터를 가져와 3,000토큰 이하의 마크다운 청크로 압축한 뒤 SQLite에 저장하며, 같은 데이터를 Obsidian(마크다운 기반 노트 앱) 호환 볼트로도 열어볼 수 있다.
- TokenJuice라는 토큰 압축 레이어가 HTML을 마크다운으로 변환하고, 긴 URL 단축, 중복 제거 등을 수행해 LLM(Large Language Model, 대규모 언어 모델) 비용과 지연을 최대 80%까지 줄인다고 주장한다.
- GNU 라이선스의 오픈소스이지만, 기본 설정에서 계정 인증, 모델 라우팅, 웹 검색, OAuth 연동 등이 OpenHuman 관리형 백엔드를 경유한다. 완전한 로컬 실행을 원하면 별도 설정이 필요하다.
- AI 에이전트의 핵심 병목이 "지능"이 아니라 "맥락"이라는 관점에서, 데이터 수집과 기억 구조를 먼저 해결하려는 접근은 주목할 만하지만, 얼리 베타 단계의 약속과 실제 완성도 사이 거리는 직접 확인이 필요하다.

## 콜드 스타트: AI 에이전트가 풀지 못한 문제

대부분의 AI 에이전트는 콜드 스타트(cold start) 문제를 갖고 있다. 새 대화를 시작할 때마다 에이전트는 사용자에 대해 아무것도 모르는 상태에서 출발한다. Hermes Agent 같은 도구는 사용자의 작업을 관찰하면서 스스로 학습하지만, 유의미한 맥락이 쌓이려면 며칠에서 몇 주가 걸린다. OpenClaw는 플러그인을 통해 외부 데이터를 가져오는 구조인데, 어떤 플러그인을 설치하고 어떤 데이터를 연결할지를 사용자가 직접 결정해야 한다.

OpenHuman의 접근은 다르다. "학습 기간 없이, 연결하면 바로 파악한다"는 것이다. 사용자가 Gmail, Slack, Notion, GitHub 같은 서비스 계정을 OAuth(사용자 비밀번호를 직접 넘기지 않고 서비스 간 접근 권한을 위임하는 인증 표준)로 연결하면, 20분 간격의 자동 동기화 루프가 각 서비스에서 데이터를 끌어온다. 한 번의 동기화만으로 에이전트가 사용자의 이메일, 캘린더, 저장소, 문서, 메시지에 대한 전체 맥락을 확보한다는 주장이다. 이 아이디어의 원천은 안드레이 카파시(Andrej Karpathy, 전 OpenAI 및 Tesla AI 책임자)가 제안한 "LLM 지식 베이스" 워크플로다. 자신의 모든 지식과 메모를 마크다운 파일로 정리해서 LLM이 읽을 수 있는 형태로 관리하자는 발상이었다.

## 메모리 트리: 기억하는 에이전트의 구조

OpenHuman의 기술적 핵심은 메모리 트리(Memory Tree)라는 로컬 지식 베이스다. 동작 방식을 단계별로 풀어보면 이렇다.

연결된 서비스에서 가져온 데이터를 3,000토큰 이하의 마크다운 청크(chunk, 일정 크기로 나눈 텍스트 조각)로 분해한다. 각 청크에 점수를 매기고, 계층적 요약 트리(hierarchical summary tree)로 접어서 SQLite(파일 하나로 동작하는 경량 데이터베이스) 에 저장한다. 동일한 청크가 `.md` 파일로도 저장되어 Obsidian 호환 볼트(vault, Obsidian에서 하나의 지식 저장소 단위)로 열어볼 수 있다.

이 설계의 장점은 두 가지다. 첫째, 모든 데이터가 사용자의 로컬 머신에 저장된다. 원본 데이터를 클라우드에 올리지 않는다. 둘째, Obsidian 볼트 형태이기 때문에 사용자가 직접 열어보고, 검색하고, 편집할 수 있다. AI가 무엇을 기억하고 있는지를 사용자가 확인하고 통제할 수 있는 구조다.

다른 코딩 에이전트(Claude Code, Cursor, Codex 등)에서 이미 agentmemory를 사용하고 있다면, OpenHuman의 메모리 백엔드를 agentmemory로 연결하는 설정도 제공한다. `config.toml` 에서 `memory.backend = "agentmemory"` 로 지정하면 동일한 메모리 저장소를 여러 에이전트가 공유할 수 있다. 에이전트마다 기억이 따로 노는 문제를 해결하려는 시도인 셈이다.

## 118개 연동과 20분 동기화 루프

OpenHuman은 Composio라는 커넥터 레이어를 통해 118개 이상의 서드파티 서비스와 연동한다. Gmail, Notion, GitHub, Slack, Stripe, Google Calendar, Google Drive, Linear, Jira 등이 포함된다. 각 연결은 원클릭 OAuth로 이루어지며, 연결된 서비스는 에이전트에게 타입이 지정된 도구(typed tool)로 노출된다.

핵심은 auto-fetch 메커니즘이다. 20분마다 활성화된 모든 연결을 순회하면서 새로운 데이터를 메모리 트리로 가져온다. 사용자가 폴링 루프를 직접 작성하거나 "이 데이터를 가져와"라고 프롬프트를 입력할 필요가 없다. 에이전트가 "오늘 아침에 이미 내일의 맥락을 갖고 있다(the agent already has tomorrow's context this morning)"는 것이 프로젝트 측의 표현이다.

다만 이 연동의 기본 경로는 OpenHuman의 관리형 백엔드를 거친다. OAuth 핸드셰이크(인증 절차)와 연동 도구 호출이 OpenHuman 서버를 통해 프록시된다. 자체 Composio API(Application Programming Interface, 서비스 간 통신 규약) 키를 사용해 직접 모드(direct mode)로 전환할 수 있지만, 그 경우 실시간 트리거 웹훅(webhook, 이벤트 발생 시 자동 호출되는 HTTP 요청)을 직접 호스팅하고 연결해야 한다. 편의와 자율성 사이의 트레이드오프다.

## TokenJuice: 토큰을 짜내는 압축 레이어

LLM을 활용할 때 비용과 지연의 상당 부분은 토큰 수에서 온다. 이메일 본문, 웹 스크래핑 결과, API 응답 같은 원시 데이터는 실제로 LLM이 필요로 하는 정보에 비해 토큰을 훨씬 많이 소비한다. HTML 태그, 중복 헤더, 불필요하게 긴 URL 같은 것들이다.

TokenJuice는 이 문제를 겨냥한 토큰 압축 레이어다. 모든 도구 호출 결과, 스크래핑 데이터, 이메일, 검색 결과가 LLM에 전달되기 전에 이 레이어를 거친다. HTML을 마크다운으로 변환하고, 긴 URL을 단축하며, 중복되거나 장황한 도구 출력을 요약한다. CJK(Chinese, Japanese, Korean) 문자와 이모지 같은 멀티바이트 텍스트는 문자(grapheme) 단위로 보존해서 잘리지 않는다. OpenHuman 측은 이를 통해 비용과 지연을 최대 80%까지 줄일 수 있다고 주장한다.

80%라는 수치가 어떤 벤치마크에서 나온 것인지, 어떤 유형의 데이터에서 그 정도 압축이 가능한지에 대한 상세한 근거는 현재 문서에서 확인하기 어렵다. 다만 HTML 태그 제거와 URL 단축만으로도 웹 스크래핑 결과의 토큰 수가 크게 줄어드는 것은 실무에서 흔히 경험하는 사실이다.

## 데스크톱 앱, 마스코트, 그리고 내장 도구

OpenHuman은 터미널이 아니라 데스크톱 앱을 기본 인터페이스로 삼는다. 설치 후 몇 번의 클릭으로 에이전트가 동작하는 경험을 목표로 하며, macOS(Homebrew), Linux(apt, AUR, AppImage), Windows(MSI) 모두 지원한다.

```bash
# macOS
brew tap tinyhumansai/core
brew install openhuman

# Linux (Debian/Ubuntu)
curl -fsSL https://tinyhumansai.github.io/openhuman/apt/KEY.gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/openhuman.gpg
echo "deb [signed-by=/etc/apt/keyrings/openhuman.gpg arch=amd64] \
  https://tinyhumansai.github.io/openhuman/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/openhuman.list
sudo apt-get update && sudo apt-get install -y openhuman
```

특이한 점은 데스크톱 마스코트다. 화면에 표시되는 캐릭터가 말하고, 주변 상황에 반응하며, 사용자가 타이핑을 멈춰도 백그라운드에서 계속 사고한다. Google Meet에 실제 참여자로 들어가는 기능도 있다. 음성 입력(STT, Speech-to-Text, 음성을 텍스트로 변환)과 ElevenLabs TTS(Text-to-Speech, 텍스트를 음성으로 변환) 출력을 지원하며, 마스코트의 입 모양이 음성에 동기화된다.

내장 도구로는 웹 검색, 웹 페이지 스크래퍼, 코더 도구셋(파일 시스템, git, 린트, 테스트, grep)이 기본 제공된다. "파일을 읽으려면 플러그인을 설치하세요" 같은 마찰이 없다는 점을 강조한다. 모델 라우팅도 내장되어 있어 작업 유형(추론, 빠른 응답, 비전)에 따라 백엔드가 적절한 LLM을 선택하고 프록시한다. 하나의 구독으로 여러 모델을 사용하는 구조이며, Ollama를 통한 로컬 모델 실행도 선택적으로 지원한다.

## 오픈소스 라벨 아래의 실제 구조

OpenHuman의 라이선스는 GNU(자유 소프트웨어 재단의 오픈소스 라이선스)다. 소스 코드를 공개하고 커뮤니티 기여를 받는다. 하지만 "오픈소스"라는 라벨 아래의 실제 아키텍처를 들여다보면 주의할 지점이 있다.

기본 설정에서 계정 로그인, 모델 라우팅, 웹 검색 프록시, OAuth 연동 흐름이 모두 OpenHuman의 관리형 백엔드를 경유한다. 소스 코드가 공개되어 있더라도, 실제 사용 경험은 OpenHuman 서버에 상당 부분 의존한다는 뜻이다. 자체 모델, 검색, Composio 자격 증명을 사용하는 커스텀 설정을 선택할 수 있지만, 일부 실시간 트리거와 호스팅 기능은 여전히 관리형 백엔드가 필요하다고 문서에 명시되어 있다.

이것은 최근 오픈소스 AI 프로젝트들에서 반복되는 패턴이다. 코드는 공개하되, 가장 편리한 기본 경험은 자사 서비스를 경유하게 설계한다. 사용자에게 선택지가 있지만, 가장 쉬운 경로가 관리형 서비스를 향한다. 이 구조가 나쁘다는 뜻이 아니라, "오픈소스니까 완전히 자급자족할 수 있다"는 기대와 현실 사이에 간극이 있다는 점을 인식해둘 필요가 있다.

## 경쟁 도구와의 비교, 그리고 빠진 맥락

OpenHuman은 자체 문서에서 Claude Cowork, OpenClaw, Hermes Agent와 비교표를 제시한다. 자사가 직접 작성한 비교인 만큼, 프레이밍이 유리한 쪽으로 기울어 있다는 점은 감안해야 한다.

비교의 핵심 축은 네 가지다. 시작 경험(데스크톱 UI vs 터미널), 메모리(메모리 트리 vs 대화 범위/플러그인 의존/자기 학습), 연동 수(118개 이상 원클릭 OAuth vs BYO, Bring Your Own), 비용 구조(하나의 구독 vs 개별 모델 API 키 관리)다. 네 축 모두에서 OpenHuman이 자신에게 최고점을 매긴다.

이 비교에서 빠진 맥락도 있다. Claude Code는 코딩에 특화된 에이전트이지 범용 개인 비서가 아니다. 용도가 다른 도구를 같은 표에 놓는 것 자체가 공정한 비교라 보기 어렵다. "하나의 구독으로 모든 모델"이라는 구조는 편리하게 들리지만, 구독 가격과 사용량 제한이 실제로 어떤지가 핵심 변수다. 얼리 베타 단계에서 구독 모델의 지속 가능성까지 판단하기는 이르다.

## 커뮤니티 의견

긱뉴스에서는 두 가지 대조적인 시각이 드러난다. 바이브 코딩(AI를 활용한 빠른 프로토타이핑)의 진입 장벽이 낮아지면서 비슷한 에이전트 하네싱(agent harnessing) 앱들이 하루가 멀다 하고 쏟아진다는 피로감이 있다. AI 에이전트 래퍼(wrapper) 프로젝트가 급증하는 현실에서, "또 하나의 에이전트 껍데기 아니냐"는 냉소적 반응이다. 반면, LLM 위키 내장 기능이 OpenClaw보다 나아 보여서 직접 써보고 싶다는 반응도 있다. 메모리 트리와 옵시디언 통합이라는 구체적 기능 차별점이 관심의 포인트인 셈이다. 동일한 프로젝트를 놓고 "범람하는 래퍼 중 하나"로 보느냐, "메모리 구조에서 차이를 만든 시도"로 보느냐가 갈리는 것이 현재 AI 에이전트 생태계의 축소판이기도 하다.

## 핵심통찰

AI 에이전트의 경쟁 축이 "모델이 얼마나 똑똑한가"에서 "사용자를 얼마나 잘 아는가"로 옮겨가고 있다는 신호가 곳곳에서 감지된다. OpenHuman의 접근, 즉 연결된 서비스에서 데이터를 자동 수집하고 로컬 메모리 트리로 압축해 에이전트에게 먹이는 구조는 이 방향의 초기 해법 중 하나다. 다만 "몇 분 만에 나를 파악한다"는 약속, GNU 오픈소스라는 라벨, 그리고 관리형 백엔드에 상당 부분 의존하는 현실 사이의 간극은 직접 써보기 전에는 판단하기 어렵다. 얼리 베타라는 점을 감안하면 지금 주목할 것은 완성도보다 설계 방향이다. "에이전트가 똑똑해지려면 먼저 기억해야 한다"는 전제가 맞다면, 메모리 우선(memory-first) 접근은 앞으로 더 많은 프로젝트에서 따라올 패턴이 될 것이다.
