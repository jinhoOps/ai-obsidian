# 📄 OpenHuman: '나를 아는 AI 비서'를 오픈소스로 만들 수 있을까

> **원문 URL**: https://wikidocs.net/blog/@jaehong/15506/

## 📌 개요

[[openhuman]]은 로컬 메모리 트리(Memory Tree)와 118개 이상의 서드파티 연동을 결합한 오픈소스 AI 에이전트 비서입니다. 기존 AI 비서들의 고질적인 문제인 **콜드 스타트(Cold Start)** 문제를 해결하기 위해, 사용자의 계정을 연결하여 디지털 맥락을 자동으로 로컬에 수집하고 압축해 기억하는 '메모리 우선(Memory-first)'의 설계 철학을 제안합니다.

---

## 🔑 핵심 내용

### 1. 콜드 스타트 문제 극복 및 자동 동기화
* **콜드 스타트(Cold Start)**: AI 에이전트가 새로운 대화를 시작할 때마다 사용자에 대한 정보를 잃고 처음부터 다시 설명해야 하는 문제입니다.
* **해결책**: Gmail, Slack, Notion, GitHub 등의 서비스를 OAuth로 연결하고, 20분 간격의 자동 동기화 루프(auto-fetch)를 작동시켜 백그라운드에서 데이터를 수집합니다. 
* **설계적 유래**: 안드레이 카파시(Andrej Karpathy)가 제안한 "모든 지식과 메모리를 마크다운으로 정리해 LLM이 읽게 하자"는 지식 베이스 워크플로에서 영감을 얻었습니다.

### 2. 메모리 트리(Memory Tree) 아키텍처
* **데이터 흐름**: 가져온 데이터를 3,000토큰 이하의 마크다운 청크로 쪼개고, 각 청크의 우선순위 점수를 매겨 계층적 요약 트리(Hierarchical Summary Tree)로 빌드한 후 로컬 SQLite에 저장합니다.
* **통제성 확보**: 수집 및 요약된 청크는 `.md` 파일 형태로도 저장되므로, 사용자는 Obsidian 볼트(vault)를 통해 AI가 무엇을 기억하고 있는지 직접 확인하고 수정할 수 있습니다.
* **메모리 백엔드 공유**: `config.toml` 설정을 통해 다른 코딩 에이전트 환경(예: [[claude-code]], Cursor 등)에서 사용하는 `agentmemory` 백엔드와 데이터베이스를 공유할 수 있어 에이전트 간의 기억 분절 문제를 방지합니다.

### 3. TokenJuice: 토큰 압축 레이어
* **문제점**: HTML 태그, 복잡한 API 응답, 불필요한 URL 등으로 인해 LLM 호출 시 발생하는 엄청난 비용과 지연 시간을 해결해야 합니다.
* **해결책**: 모든 데이터를 LLM에 넘기기 전에 [[token-compression]] 기술을 구현한 **TokenJuice** 레이어를 경유시킵니다. HTML을 마크다운으로 바꾸고, 긴 URL 단축 및 중복 요약을 통해 토큰 비용과 대기 시간을 최대 80% 줄인다고 주장합니다. CJK 문자열과 이모지 등은 깨지지 않도록 문자(grapheme) 단위로 보존합니다.

### 4. 오픈소스 라벨과 관리형 백엔드 의존성
* **하이브리드 구조**: GNU 라이선스의 오픈소스 프로젝트이나, 기본적으로 인증(OAuth), 모델 라우팅, 웹 검색 프록시 등이 OpenHuman의 관리형 백엔드 서버를 거치게 되어 있습니다.
* **한계와 대안**: 완전한 로컬 단독 구동(direct mode)을 위해서는 자체 Composio API 키 발급 및 실시간 트리거용 웹훅 호스팅을 직접 해결해야 하는 트레이드오프가 존재합니다.

## 💭 생각 및 메모 (사용자 맥락)

> "써보고 여기 프로젝트에 도입하려고 캡처함. 테스트 잘되면 ai-obsidian 여기 방식(현재 AI 에이전트 기반 지식 관리 프레임워크)을 변경할 수도 있음. 일단 무엇인지 컨셉을 정확히 파악하고 주요 기능을 모두 사용해보는 것이 우선 목표."

* **연계 제언**:
    * OpenHuman의 핵심인 '백그라운드 자동 동기화'와 'Obsidian 볼트 저장'은 `ai-obsidian` 프로젝트가 지향하는 AI-인간 협업 지식 저장소 모델과 개념적으로 매우 밀접합니다.
    * 만약 도입을 검토한다면, 프라이버시가 침해되지 않도록 `direct mode` 설정(Composio 직접 세팅 및 자체 로컬 웹훅)에 따른 인프라 수고와 관리형 서버 편의성 간의 트레이드오프를 확인하는 테스트 단계가 필수적일 것입니다.
